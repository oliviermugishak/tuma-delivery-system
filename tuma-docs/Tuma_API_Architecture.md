# Tuma — API Architecture

**Status:** approved foundation for V1 (iteration "Foundations", 2026-08-27).
Companion doc: `Tuma_Auth_and_RBAC_Architecture.md` (identity, tokens, roles).

---

## 1. Principles

1. **The API is the product's contract.** Three clients consume it — the Flutter app, the web platform, and (later) partner integrations. The OpenAPI document is the single source of truth for that contract.
2. **The server owns truth.** Prices, order state, delivery location, roles — clients display, they never decide.
3. **Boring and predictable beats clever.** REST, JSON, stable envelopes, additive evolution. No GraphQL, no WebSocket, no event bus until something measurably hurts.

## 2. URL structure

One API, three audiences, versioned root. Actor namespaces make RBAC visible in the URL tree:

```
/api/health                        unversioned infra probe (load balancers, uptime)

/api/v1/openapi.json               the contract
/api/v1/auth/otp/request    POST   public      → customer passwordless login
/api/v1/auth/otp/verify     POST   public
/api/v1/auth/login          POST   public      → email+password, sets session cookies
/api/v1/auth/logout         POST   authenticated
/api/v1/auth/password       POST   authenticated
/api/v1/me                  GET    any role    → {user, role}
/api/v1/me                  PATCH  any role    → complete profile (name)

/api/v1/stores              GET    public      (next iteration)
/api/v1/stores/:id          GET    public      (next iteration)
/api/v1/orders …            …      customer    (next iteration)

/api/v1/admin/merchants     POST, GET          [admin]
/api/v1/admin/merchants/:id PATCH              [admin]

/api/v1/merchant/…          …                  [merchant]   (next iteration: store, products, orders)
/api/v1/rider/…             …                  [rider]      (later: location push)
```

Rules:
- Kebab-case/plural nouns, ids in path, filters in query strings.
- Everything business lives under `/api/v1`; only `/api/health` is unversioned.
- A route's namespace decides its default audience; the role guard enforces it.

## 3. Versioning policy — version-tolerant by rule

- **Within v1: additive only.** Add fields, add endpoints, add enum values where the DB enum allows it. Never rename, remove, or retype a field; never change units or timestamp formats.
- **Clients must ignore unknown fields.** All three clients deserialize leniently (Dart `json` by hand, TypeScript via generated types with open-ended fallback, serde with `deny_unknown_fields` *off* — the default).
- **A true break earns `/api/v2`.** The old version stays alive as long as app builds in the wild need it; v2 is a fork of the router tree, not a rewrite of the domain.
- Enum additions (e.g. order status) are only shipped together with clients that handle them; unknown enum values from the server must render as a graceful fallback in every client.

## 4. Error envelope

Every non-2xx response uses one shape (already implemented as `ApiErrorResponse`):

```json
{
  "error": "validation_failed",
  "message": "Input validation failed",
  "details": [{ "field": "phone", "message": "invalid phone number" }]
}
```

| `error` code | HTTP status | Meaning |
|---|---|---|
| `validation_failed` | 422 | payload failed validation, `details` present |
| `bad_request` | 400 | malformed JSON / structurally wrong input |
| `unauthorized` | 401 | missing/invalid/expired credentials |
| `forbidden` | 403 | authenticated but wrong role / not owner |
| `not_found` | 404 | no such resource (or hidden from this caller) |
| `conflict` | 409 | duplicate (email, phone) or illegal state transition |
| `database_error` / `internal_error` | 500 | generic message only — internals never leak |

## 5. Conventions

- **Ids:** UUIDv4, generated by Postgres (`gen_random_uuid()`).
- **Money:** integer RWF (BIGINT). Never floats, never cent strings. `1500` means 1,500 RWF.
- **Timestamps:** ISO-8601 with timezone (`TIMESTAMPTZ` → RFC 3339 in JSON), UTC on the wire.
- **Status codes:** 200 reads · 201 creates (body = created resource) · 204 auth mutations & logout · 422 validation · see §4.
- **Inputs:** validated at the door (`ValidatedJson` + `validator` derive); handlers never see unvalidated payloads.
- **Auth:** Bearer header (mobile) or session cookies (web) — see the auth doc; handlers see only `UserContext`.

## 6. OpenAPI contract & client generation pipeline

```
 tuma-server (utoipa)
 ├─ served live:  GET /api/v1/openapi.json
 └─ exported:     cargo run --bin export_openapi -- <file>     (no server needed)
        │
        │  ./run.sh openapi
        ▼
 tuma-platform/openapi.json            (committed, regenerated per API change)
        │
        │  pnpm generate:api  (Orval)
        ▼
 tuma-platform/src/api/generated/      (typed client + TanStack Query hooks —
                                        NEVER hand-edited; diffs reviewed like code)

 tuma-app (Flutter)
 └─ hand-written client in lib/core/api/ — reads the same OpenAPI doc as a human,
    writes typed Dart per slice. Deliberate choice: the mobile client stays
    small, explicit, and founder-written.
```

Rules:
- Every endpoint lands with its `#[utoipa::path]` annotation in the same slice (server checklist in `AGENTS.md`) — the contract can never lag the implementation.
- After any API change: `./run.sh openapi` + `pnpm generate:api`, and the generated diff is part of the review.
- The spec file is committed so platform builds never depend on a running server.

## 7. Client matrix

| Client | Auth transport | API client | State |
|---|---|---|---|
| Flutter app (customer, later rider) | Bearer JWT in secure storage | hand-written Dart (`lib/core/api/`) | Riverpod |
| Platform web (admin + merchant) | httpOnly session cookies | Orval-generated fetch + TanStack Query | TanStack Query (server state) |
| curl / partners | Bearer or cookies | — | — |

## 8. Scalability posture (documented now, built when needed)

- **Stateless request path.** JWT verification needs no shared memory → any server instance serves any request; horizontal scaling is adding instances behind a load balancer. (Silent refresh does one DB lookup — fine.)
- **Postgres is the single source of truth.** One schema (`tuma`), migrations numbered and reviewed. Read replicas later if reads hurt.
- **Tracking stays polling** (rider pushes ~5s, customer polls ~3s) until real load says otherwise; the upgrade path is a streaming endpoint, not a new architecture.
- **Redis/Kafka: not before measured need.** `redis:7` is on the machine for the day we need a cache/rate-limiter/queue; nothing in V1 requires it.
- **OTP/refresh rows are tiny**; cleanup jobs (expired rows) land when the tables are visibly growing.

## 9. Deployment & transport notes

- **Cookie sessions are same-site by design.** In dev the platform's Vite dev server proxies `/api → 127.0.0.1:8080`, so the browser sees one origin — no CORS, cookies flow. In production, serve the platform and API on the same site (e.g. `app.tuma.rw` + `api.tuma.rw` with matching site, or a single domain behind a proxy) and list every frontend origin in `TUMA_CORS_ORIGIN`.
- The mobile app talks to the API directly (Bearer — no cookie/CORS story needed). Android emulator reaches the dev server at `10.0.2.2:8080`; real devices use the LAN IP.
- TLS terminates at the proxy in production; `cookie_secure: true` assumes HTTPS.
