## Identity

Tuma is a commerce + delivery platform starting with food in Kigali.

The product in one sentence: *a mobile app to view merchants and their
products, add to cart, order, checkout, and watch the delivery move on a
real map.*

The killer feature is **real delivery tracking** — real GPS from a real
phone, drawn on a real map. Never simulated.

## Locked decisions (founder)

- **Crates-only architecture (2026-08-30):** `tuma-server/src/` contains ONLY the API layer — routes, middleware, error mapping, wiring. Never write domain/business logic in `src/`; every domain lives in its own workspace crate (`accounts`, `commerce`, `marketplace`, `storage`, `app-config`) with its tests. The `domain` folder must not exist.
- **Backend is Rust** (Axum + SQLx + PostgreSQL). The founder thinks in Rust; TypeScript and Python ways were explicitly rejected. (2026-08-27)
- **Monorepo layout:** `tuma-server/`, `tuma-app/`, `tuma-platform/`, `tuma-docs/`. (2026-08-27)
- **Flutter app is a fresh start** from `flutter create` — nothing reused from the old prototype, not even seed data. (2026-08-27)
- **Visual identity = evolve-emerald:** keep emerald `#0B6E4F` / orange `#FF7A1A` / greige `#F7F7F5` + Poppins/Inter, rebuild every component from the roots at a higher polish level. (2026-08-27) — **Superseded 2026-08-27** by the founder's brand palette (next item).
- **Brand palette (founder):** gold `#FDBB01` (primary), orange `#FC7701` (primaryDeep / emphasis), deep navy `#0B1A3D` (surfaceAlt), very dark navy `#061323` (surface / background + onPrimary text), light blue-gray `#D3DEE9` (onSurface text). Dark theme. Tokens live ONLY in `tuma-app/lib/core/theme/app_colors.dart` — no raw hex anywhere else. Poppins carries headlines, Inter body. (2026-08-27)
- **tuma-platform stays a template** until V1.5 (merchant web) / V2.5 (admin). Stack deliberately undecided. (2026-08-27)
- **Server house style mirrors `~/Work/projects/kanombe-sda`**: layered YAML config (`config` + dotenvy + secrecy), compile-time-checked SQLx with offline `.sqlx` caches, numbered `NN_name.sql` migrations in a `tuma` schema, UUID PKs, `updated_at` triggers, BIGINT RWF money, bunyan tracing, utoipa OpenAPI, `#[sqlx::test]` integration harness, postgres-only dev compose. (2026-08-27)
- **Dev database = `postgres:18`** via docker compose. `redis:7` exists on the machine and joins only when a real need appears. (2026-08-27)
- **Hand-to-hand contract:** every feature reviewed by the founder; every Flutter line written with the founder; every slice starts as a few approved lines of design before code. (2026-08-27)
- **Simplicity budget for V1:** 6 tables, ~10 endpoints, 6 order statuses (`placed, accepted, preparing, picked_up, delivered, cancelled`). Cash-on-delivery first; MTN MoMo after the loop works. (2026-08-27)
- **The TypeScript scaffold** (pnpm workspace, Fastify, packages/*) **was removed** — superseded by the Rust decision. The v2.0 blueprint's Fastify chapters are reference-only. (2026-08-27)
- **Foundations before features:** auth + RBAC are built before stores/products. The iteration order is: identity on the API → mobile splash/login/home on the real API → platform admin + merchant wings → then stores/products. (2026-08-27)
- **Three roles in V1:** `customer`, `merchant`, `admin` (of the blueprint's nine; mapping + promotion path documented in the auth doc). Merchant accounts are **created by admin** — no self-signup in V1. (2026-08-27)

Dev OTP is a fixed code from `local.yml`. (2026-08-27)

(2026-08-28)

- **Phone numbers are customer identity only.** Merchant/admin accounts are email + password, never phone — merchant creation takes no phone field (it caused cross-identity unique collisions reported with the wrong message). (2026-08-28)
- **Phones are E.164 with an explicit country code — `+250783002002` — everywhere, or they are rejected (2026-08-31).** The founder's call after the admin form's free-text `0783002002` and the mobile's `+250783002002` created TWO identities for one real phone (a rider account + a phantom customer; the rider was unreachable from the app and OTP verify silently ensured a customer profile on the phantom). No normalization, no country guessing: `validate_phone` requires `+` + 9–15 digits (422 "include the country code, e.g. +250783002002"); the platform dialogs refuse to submit without the `+` (inline error, full-number placeholder/hints); the mobile already always prepends its dial code. Trimming is the only processing anywhere. Dev-data remedy for the two divergent rows: delete via the admin pages (no migration).
- **One `users` identity table for all three roles — no customer/merchant split.** Merchant "more info" lands in domain tables (`stores` first, per the brief); if merchant-only profile data ever appears, a `merchant_profiles` table referencing `users(id)` is additive. Splitting identity would rewrite auth for no V1 gain. (2026-08-28)
- **AccountManager pattern** (kanombe-sda shape): `accounts::AccountManager` owns account creation + all password work (hash/verify gated by a semaphore, dummy-hash timing equalization, change password). Handlers/tests/bins never touch argon2 directly. Typed `CreateAccountError::{EmailTaken, PhoneTaken}` resolved from the Postgres constraint name — clients always get the identity that actually collided. (2026-08-28)
- **Platform is a plain Vite SPA** — TanStack Start/SSR removed (it dehydrated routes as loaded so client route guards never ran: infinite loading, zero API requests). Login-gated internal tooling; SSR had no value. (2026-08-28)
- **Dashboard pages never center page content** (no `mx-auto max-w-*` wrappers) — full width, left-aligned. Centering is only for the login screen and small in-card states. (2026-08-28)
- **Storefront iteration scope (founder):** storefront only — cart/checkout/orders are the NEXT iteration (build order #3, own plan). App bottom bar = **Home + Profile** now; the shell is built so Search and Orders tabs slot in when those features exist (blueprint 7.1's full bar is Home • Search • Orders • Profile). (2026-08-28)
- **Multi-store merchants (founder):** a merchant can have SEVERAL stores — supersedes S9's one-store-per-merchant. `stores.merchant_id` is no longer UNIQUE (migration 04 swapped the unique constraint for a plain index). Merchant API is a stores collection: `POST/GET /v1/merchant/stores`, `GET/PATCH /v1/merchant/stores/{id}`; products: `GET /v1/merchant/products` (across all own stores) and `POST` with a required `store_id` — ownership-checked, unknown/foreign store → 404 "store not found". Customer endpoints untouched. (2026-08-28)
- **Platform UI standard (founder, lasting):** roomy, professional, system-like — compacted layouts are banned for good. Page headers `mb-8 flex flex-wrap items-start justify-between gap-4`, title `font-heading text-2xl font-semibold tracking-tight`, subtitle `mt-1.5 max-w-xl text-sm text-muted-foreground`; cards `p-6`; store grids `grid gap-6 lg:grid-cols-2`; identity tiles are custom divs (`size-12`/`size-14 rounded-xl|2xl bg-primary/10 font-heading text-primary`), not Avatar; empty states `py-16`–`py-24` with an icon tile and one action; table cells `py-3.5`; `space-y-6` between cards. (2026-08-28)
- **Image uploading is crucial but deliberately deferred (founder):** robust upload for store and product images comes later; the `image_url` columns already exist in the DB and API and wait for it. Not in the storefront iteration. (2026-08-28)
- **Test discipline (founder, system-wide rule):** every test must earn its place. No redundant tests for non-critical paths — tests that exist only to slow CI down while testing nothing special are banned. Cover the behavior that matters (ownership, money, auth, state transitions); skip ceremony and duplicates. (2026-08-28)
- **Agents never run the full suite (founder, 2026-08-30):** whole-suite runs (`cargo test --workspace`, whole-file `flutter test`) crash and waste time. Agents run ONLY their slice's new tests (`cargo test --test <area>`, `flutter test --plain-name "<name>"`); when the new tests pass their feature, they move on — the founder runs the global suite himself. Recorded in AGENTS.md.
- **Placeholder imagery = verified Unsplash CDN URLs (founder guide):** store/product `image_url`s stay null until the upload slice exists; the app's `RemoteImage` shared widget renders the real URL when present, else a deterministic placeholder (djb2 hash of the name into a pool of 10 curl-verified URLs in `core/constants/placeholder_images.dart`), else a gradient block. When uploading lands, real URLs simply win — no UI changes. (2026-08-28)
- **Orders iteration O1+O2 done (2026-08-28):** Migration 05 creates `order_status` enum, `orders`, `order_items`, `deliveries` tables. New `commerce` crate owns the full order domain. Three customer endpoints live under `POST /v1/orders`, `GET /v1/orders`, `GET /v1/orders/{id}`. Another customer's order returns 404 indistinguishable from missing. Item name + price snapshotted at order time. 7 integration tests. Merchant + admin order endpoints (O3) pending. — **Superseded 2026-08-29** by the marketplace re-architecture (below): orders → store orders under order groups.
- **Marketplace re-architecture (founder directive + approved merged plan, 2026-08-29):** the entire domain was re-engineered around a real multi-merchant, multi-store marketplace. (1) **Identity split from business entities:** `users` becomes the central ACCOUNT (phone/email/password/is_active, `role` column dropped); `customers`, `admins` are profile rows; `merchants` is the BUSINESS (no login); `merchant_memberships (user_id, merchant_id, role owner|manager, store_id?)` authorizes — store_id NULL = all stores (owner), set = that one store (store manager). JWT carries account id only; guards are capabilities (`require_customer/require_admin/require_merchant`), resolved fresh per request. (2) **Store = fulfillment boundary:** `products` is the merchant CATALOG; `store_products (store_id, product_id, price, stock? NULL=untracked, is_available, sku?)` is what customers buy — per-store price/stock/availability, UNIQUE(store_id, product_id). (3) **Checkout:** one `order_group` (address snapshot, money totals, idempotency key UNIQUE(user_id, key), no status column) → one `store_order` per participating store (six-value status + existing transitions) → `order_items` (store_order_id, store_product_id + product_id, name/price snapshots) → one `deliveries` row per store order. Group state is DERIVED (`in_progress | partially_fulfilled | completed | cancelled`), never stored. (4) **Payments:** one `payments` row per group (cash_on_delivery, pending|collected|refunded) + `payment_allocations` per store order (pending|settled|refunded) — merchant money is explicitly allocated, never inferred. Collection is manual by admin until MoMo. (5) **Checkout is transactional + idempotent**, all-or-nothing (409 names the closed store / unavailable product / short stock); stock reserved by conditional UPDATE inside the transaction. (6) **Fresh migration chain** 00_schema/01_identity/02_marketplace/03_commerce replaces 00–05; dev DB reset approved (founder test data re-created via the wing). Deliberately deferred: discounts/tax columns (until promotions), refunds table, settlements, saved-addresses, staff-invite UI (enforcement is live), webhook handling (cash has none). Founder-tunable defaults locked: manual cash collection, 4 derived group labels.
